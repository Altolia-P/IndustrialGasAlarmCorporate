> 将现有单体应用改造为微服务架构，作为面试主打项目展示分布式技术栈能力。

## 一、服务拆分方案

### 1.1 拆分结果（4 个服务 + 1 个网关）

```
                    ┌─ Nacos (注册中心 + 配置中心)
                    │
Browser ─→ Gateway ─┼─ Auth Service      (认证鉴权 + 员工管理)
                    ├─ CMS Service       (产品/内容/分类/留言)
                    └─ Device Service    (设备/报警/通知/工单)
```

### 1.2 各服务业务边界与拆分理由

| 服务 | 数据库表 | 业务职责 | 独立理由（面试必问） | 负载特征 |
|------|---------|---------|-------------------|---------|
| **Gateway** | 无 | 路由转发、全局鉴权、令牌桶限流、跨域 | 鉴权与限流从业务剥离，无状态可无限水平扩展 | 所有流量必经 |
| **Auth Service** | `t_admin_user`, `t_staff`, `t_operation_log` | 登录认证、JWT 签发/校验、黑名单、员工管理、操作审计 | 安全边界独立，JWT 签发密钥集中于一点管理 | 低频但敏感 |
| **CMS Service** | `t_product`(+子表), `t_content`, `t_category`, `t_contact_message`, `t_system_config` | 产品展示(前台+后台)、解决方案、分类管理、留言收集与处理、系统配置 | ToB 官网读多写少，缓存策略最密集，与 IoT 读写模式完全不同 | 读密集型 |
| **Device Service** | `t_device`, `t_device_data_point`, `t_alert_rule`, `t_alert`, `t_notification`, `t_work_order`, `t_event_outbox` | 设备数据接入、报警引擎评估、通知管理、工单管理 | IoT 数据写入 QPS 高，报警引擎 CPU 密集计算，须独立扩缩容 | 写密集型 |

### 1.3 服务调用关系

```
Gateway ──(鉴权)──> Auth Service
Gateway ──(路由)──> CMS Service
Gateway ──(路由)──> Device Service
Device Service ──(Feign)──> Auth Service     (获取员工信息用于工单指派)
Alert Engine ──(Feign)──> CMS Service        (报警关联产品/解决方案)
Auth Service ──(outbox/MQ)──> CMS Service    (账户锁定通知前台)
```

## 二、技术栈升级对比

| 能力 | 当前 V1.6（已实现） | 后续升级方向 | 面试价值 |
|------|-------------------|-------------|---------|
| 注册/配置中心 | **Nacos 2.x**（device-collector 已注册） | 全服务注册 + 动态配置刷新 | ✅ 已落地 |
| 网关 | 无（直连 Controller） | **Spring Cloud Gateway** + 自定义 Filter | 路由断言、鉴权、限流 |
| 服务调用 | **OpenFeign**（DeviceDataClient 已使用） | 全服务 Feign 调用 + LoadBalancer | ✅ 已落地 |
| 熔断降级 | 无 | **Resilience4j** (CircuitBreaker) | 服务保护、降级兜底 |
| 异步消息 | **RabbitMQ**（设备事件 + 告警消费已使用） | 死信队列 + 延迟消息 | ✅ 已落地 |
| 可靠消息 | **EventOutbox 模式**（已完整实现） | Outbox 轮询投递优化 | ✅ 已落地 |
| 分布式锁 | **Redisson 3.40.2**（DashboardPushScheduler 已使用） | 工单分配防重 | ✅ 已落地 |
| 微服务拆分 | **device-collector** 已独立部署 | CMS/Auth 拆分 | 渐进式演进 |
| 分布式事务 | 无（仅 `@Transactional`） | **手动补偿 Saga**（优先）/ Seata AT 备选 | 跨服务数据一致性 |
| 容器化 | 无 | **Docker Compose** 7 容器一键启动 | 演示方便、环境一致 |
| 限流 | Redis 手机号/IP 防刷 + 12 个 Redis Repository | Gateway **令牌桶 Lua 脚本** + 业务层防刷 | 高并发限流 |

### 2.1 为何不用 Spring Cloud Alibaba 全家桶？

- **Sentinel** → 用 **Resilience4j**：轻量，不引入 Alibaba 依赖重量级配置
- **Dubbo** → 用 **Feign**：HTTP RESTful 更通用，面试更主流
- **Seata** → 用手动 **补偿 Saga**：讲解每一步回滚逻辑比用框架加分更多

## 三、Redis 使用场景汇总（11 个面试点）

### 3.1 按服务分布

| # | 场景 | 所属服务 | 数据结构 | 核心指令 | 技术亮点 |
|---|------|---------|---------|---------|---------|
| 1 | JWT 黑名单 | Auth | String + TTL | `SETEX` | Token 登出后失效，TTL 对齐 JWT 过期时间 |
| 2 | 登录失败计数 | Auth | String + INCR | `INCR` + `EXPIRE` | 5 次失败锁定 30min，原子操作防并发 |
| 3 | 网关令牌桶限流 | Gateway | String + [Lua](http://www.luascript.org) 脚本 | `EVAL` + `DECR` + `EXPIRE` | Lua 保证令牌桶的原子性，高并发友好 |
| 4 | 分类树缓存 | CMS | String(JSON) + TTL 1h | `SETEX` / `GET` | 缓存预热 + 写后主动失效，防缓存穿透(Bloom Filter) |
| 5 | 产品/内容详情缓存 | CMS | String + 主动失效 | `SETEX` / `DEL` | 写后更新策略，缓存空值防穿透 |
| 6 | 手机号防刷 60s | CMS | String + SET NX EX | `SETNX` + `EXPIRE` | 幂等性保证，同一手机号 60s 内只接受一次 |
| 7 | IP 限流 3次/min | CMS | String + INCR | `INCR` + `EXPIRE`（首次） | 滑动窗口计数器，防爬虫 |
| 8 | 设备数据滑动窗口 | Device | ZSet | `ZADD` + `ZREMRANGEBYSCORE` + `ZCOUNT` | 1h 时间窗口，score=时间戳秒数，超阈值计数 |
| 9 | 报警去重抑制 | Device | String + SET NX EX | `SETNX` + `EXPIRE` | 同设备+同规则 5min 冷却，防报警风暴 |
| 10 | Dashboard 热点缓存 | Device | String + TTL 5min | `SETEX` | 统计数据 5min 更新一次，高并发下保护 DB |
| 11 | 工单分配防重 | Device | Redisson 分布式锁 | `tryLock(leaseTime)` | 同一工单同时只能被一人接单 |

### 3.2 缓存策略设计

```
分类/产品/内容读缓存：
  ┌─ 读请求 ─> Redis GET ─> hit ─> 返回
  │             └─ miss ──> DB 查询 ─> SETEX 写回 ─> 返回
  └─ 写请求 ─> DB 更新 ─> Redis DEL（主动失效）

缓存穿透防护：
  └─ DB 查询为空时，缓存 null 值 TTL 60s，防止恶意请求击穿 DB

缓存预热（启动时）：
  └─ @PostConstruct 加载分类树 + 统计数据到 Redis，避免冷启动
```

## 七、面试高频追问准备

### Q1: 为什么拆成 4 个服务而不是更少/更多？

- **4 个正好**：Auth 是安全边界、CMS 是读密集型、Device 是写密集型，负载特征和演进节奏完全不同
- **再少**：Auth+CMS 合并会丢失"安全独立部署"的亮点
- **再多**：过度拆分，工单拆出去没有独立扩缩容场景，属于为拆而拆

### Q2: Outbox 和 RabbitMQ 是什么关系？

- **Outbox**：解决"数据库写入成功但消息发不出去"的事务一致性问题。写 DB 同时写 `t_event_outbox`，定时轮询投递
- **RabbitMQ**：解决异步解耦和削峰。Outbox 投递到 MQ，消费者异步处理
- **组合使用**：Outbox 保证 at-least-once，RabbitMQ 提供异步能力

### Q3: 跨服务数据一致性怎么保证？

以"报警创建 → 自动建工单"为例：
```
1. Device Service: 创建 Alert (本地事务)
2. 发布 AlertCreatedEvent → Outbox 投递
3. Device Service 内部处理:
   - 调用 Feign 创建 WorkOrder
   - 成功: 更新 alert.workOrderUuid
   - 失败: 工单补偿删除 + 告警标记无工单
```
这就是手动 Saga 补偿模式。

### Q4: Redis 缓存和数据库一致性？

采用 **Cache Aside** 模式：
- 读：先查缓存，miss 查 DB 并回写
- 写：先更新 DB，再删缓存
- 延迟双删：写 DB → 删缓存 → 等 500ms → 再删（工程上够用）

### Q5: 分布式锁怎么用的？

```java
// 工单接单
RLock lock = redissonClient.getLock("device:lock:workorder:" + uuid);
if (lock.tryLock(3, 10, TimeUnit.SECONDS)) {
    try {
        // 查工单状态 + 指派
    } finally {
        lock.unlock();
    }
}
```

用 Redisson 的看门狗机制自动续期，防死锁。
