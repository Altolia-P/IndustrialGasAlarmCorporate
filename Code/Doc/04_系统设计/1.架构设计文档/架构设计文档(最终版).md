### 2.3 MyBatis-Plus 与 DDD 集成说明

- **PO（持久化对象）**：放在 `infrastructure.repository.po` 包，使用 `@TableName` 注解映射表。
- **Mapper 接口**：继承 MyBatis-Plus 的 `BaseMapper<PO>`，提供基础 CRUD。
- **Repository 实现**：在 `infrastructure.repository.impl` 中注入对应 `Mapper`，负责 **PO ↔ 领域对象转换**，并实现 `domain.repository` 中定义的接口。
- **领域层无侵入**：`domain` 包中的聚合根、Repository 接口不依赖任何 MyBatis-Plus 注解或类。

### 2.4 Redis 集成与使用场景

- **缓存分类列表**：`getCategoriesByType` 查询结果缓存 1 小时，使用 `@Cacheable`（Spring Cache + Redis）。
- **表单防刷**：
  - 同一手机号 60 秒内重复提交限制，使用 Redis `SET key value EX 60 NX` 原子操作。
  - 同一 IP 每分钟最多 3 次，使用 `INCR` + `EXPIRE` 滑动窗口。
- **JWT 黑名单**（可选）：登出或修改密码时可将旧 token 加入黑名单（Redis Set，设置过期时间与 token 剩余有效期一致）。
- **分布式锁**：使用 `Redisson` 实现，用于定时任务单实例执行（DashboardPushScheduler）和工单分配防重。

## 三、基础类型与通用设计

### 3.1 统一返回类型

| 类/接口      | 说明              | 关键属性与方法                                            |
| ------------ | ----------------- | --------------------------------------------------------- |
| `Page<T>`    | 分页结果统一包装  | `content:List<T>`, `totalElements:long`, `totalPages:int` |
| `Result<T>`  | Controller 返回体 | `code:int`, `message:String`, `data:T`, `success:boolean` |
| `BaseEntity` | 审计字段基类      | `createdAt:Date`, `updatedAt:Date`                        |

**审计字段自动维护策略**：`BaseEntity` 的 `createdAt` 和 `updatedAt` 由 MyBatis-Plus 的 MetaObjectHandler 自动填充，业务代码无需手动赋值。具体配置见 3.2 节。

### 3.2 审计字段自动维护策略（适配 MyBatis-Plus）

`BaseEntity` 包含 `createdAt` 和 `updatedAt` 字段，使用 MyBatis-Plus 的 **自动填充功能** 完成赋值，无需业务代码干预。

配置示例：

```java
@Component
public class MyMetaObjectHandler implements MetaObjectHandler {
    @Override
    public void insertFill(MetaObject metaObject) {
        this.strictInsertFill(metaObject, "createdAt", Date::new, Date.class);
        this.strictInsertFill(metaObject, "updatedAt", Date::new, Date.class);
    }

    @Override
    public void updateFill(MetaObject metaObject) {
        this.strictUpdateFill(metaObject, "updatedAt", Date::new, Date.class);
    }
}
```

同时在 PO 对应字段上添加 `@TableField(fill = FieldFill.INSERT)` 等注解。

### 3.3 分页实现

MyBatis-Plus 提供 `PaginationInnerInterceptor` 分页插件，在 `MybatisPlusConfig` 中注册即可。Service 层调用 `Page<T>` 对象传入 `IPage`，Repository 实现中映射为 `Page` 返回领域对象。

### 3.4 统一错误码规范

所有 `Result` 的 `code` 遵循以下约定：

| 范围   | 含义               | 示例              |
| ------ | ------------------ | ----------------- |
| `0`    | 成功               | `0`               |
| `4xxx` | 业务异常（客户端） | `4001` 产品不存在 |
| `5xxx` | 系统异常（服务端） | `5001` 数据库错误 |

**HTTP 状态码与业务码映射**：

| 场景             | HTTP 状态码 | 业务 code 示例 |
| ---------------- | ----------- | -------------- |
| 成功             | 200         | `0`            |
| 业务异常         | 400 或 404  | `4xxx`         |
| 系统异常         | 500         | `5xxx`         |
| 未认证（未登录） | 401         | `4008`（预留） |
| 无权限           | 403         | `4009`（预留） |

前端应同时检查 HTTP 状态码和 `code` 字段，以 `code` 为准区分具体业务错误。

**错误码枚举管理**（团队级要求）：
为了避免代码中出现魔法数字，在 `common` 包中定义 `ErrorCode` 枚举类，统一管理所有业务错误码：

```java
public enum ErrorCode {
    SUCCESS(0, "成功"),
    PARAM_INVALID(4000, "参数校验失败"),
    PRODUCT_NOT_FOUND(4001, "产品不存在"),
    CONTENT_NOT_FOUND(4002, "内容不存在"),
    CATEGORY_NOT_FOUND(4003, "分类不存在"),
    MESSAGE_NOT_FOUND(4004, "留言不存在"),
    USER_NOT_FOUND(4005, "管理员不存在"),
    ACCOUNT_LOCKED(4006, "账户已锁定"),
    INVALID_PASSWORD(4007, "密码错误"),
    UNAUTHORIZED(4008, "未登录"),
    FORBIDDEN(4009, "无权限"),
    INTERNAL_ERROR(5001, "系统内部错误");
    
    private final int code;
    private final String defaultMessage;
    // 构造方法、getter
}
```

所有 `BusinessException` 子类在构造时直接接收一个 `ErrorCode`，全局异常处理器通过 `ErrorCode` 填充 `Result`，确保前后端错误码严格一致。

常见业务错误码（`BusinessException` 子类与 code 映射）：

| 异常类                      | code   | 说明              |
| --------------------------- | ------ | ----------------- |
| `ProductNotFoundException`  | `4001` | 产品不存在        |
| `ContentNotFoundException`  | `4002` | 内容不存在        |
| `CategoryNotFoundException` | `4003` | 分类不存在        |
| `MessageNotFoundException`  | `4004` | 留言不存在        |
| `UserNotFoundException`     | `4005` | 管理员不存在      |
| `AccountLockedException`    | `4006` | 账户已锁定        |
| `InvalidPasswordException`  | `4007` | 密码错误          |
| 参数校验失败                | `4000` | `@Valid` 校验汇总 |

全局异常处理会将异常转换为 `Result` 并返回对应的 `code` 和 `message`。

### 3.5 领域事件（MVP 弱化）

MVP 阶段仅保留 `MessageSubmittedEvent` 和 `AccountLockedEvent` 的定义，事件发布采用同步日志 + 预留 `EventBus` 接口，不实现异步总线。Service 层在事务提交后可直接记录日志或调用内部邮件工具类，而不是通过事件总线发布。待后续扩展时再接入 Spring Event / 消息队列。

### 4.7 AI 智能助手上下文（新增）

基于 **LangChain4j + DeepSeek** 实现，用户在前台输入问题，系统通过向量语义搜索从数据库匹配相关产品和方案，结合大模型生成推荐回复。

**核心组件**：

| 组件 | 路径 | 说明 |
|------|------|------|

| `ProductTextProvider` | infra/ai/search | 从 DB 加载已发布产品文本供 Embedding |
| `SolutionTextProvider` | infra/ai/search | 从 DB 加载已发布方案文本供 Embedding |
| `AIChatRateLimitRepository` | infra/redis | IP 级别限流：10 次/分钟 |
| `ChatSessionRepository` | infra/redis | 会话持久化：24h TTL，最多 10 轮 |

**检索策略（三级回退）**：

### 4.13 报警引擎设计（新增 V1.6）

**核心管线**：设备数据接入 → 规则匹配 → 滑动窗口判定 → 去重抑制 → 创建报警 → 事件发布

```
DeviceDataPoint 上报
    ↓
DeviceIngestionService.ingest()
    ↓ 保存数据点后触发
AlertEngineService.evaluate(dataPoint)
    ↓ 加载设备 + 匹配规则
对每条 THRESHOLD 规则：
    1. rule.evaluate(concentration) — 阈值判定
    2. DeviceDataWindowRepository.addDataPoint() — Redis ZSet 记录
    3. countExceededInWindow() — 滑动窗口计数
    4. AlertSuppressRepository.trySuppress() — 5min 去重抑制
    5. 创建 Alert + AlertRepository.save()
    6. 若 autoCreateWorkOrder → WorkOrderService.createWorkOrder()
    7. EventBus.publish(AlertCreatedEvent)
        → NotificationService.notifyAlert() — 创建通知记录
```

**Redis 组件**：

| 组件 | Key 模式 | 数据结构 | 用途 |
|------|---------|---------|------|
| DeviceDataWindowRepository | `device:window:{deviceUuid}` | ZSet（score=时间戳） | 滑动窗口数据存储，1h TTL |
| AlertSuppressRepository | `alert:suppress:{deviceUuid}:{ruleUuid}` | String（SETNX） | 5min 报警去重抑制 |
| DashboardCacheRepository | `dashboard:stats` | String（JSON） | 大屏统计缓存，5min TTL |

**关键设计决策**：
- 报警去重：同一设备+同一规则，5分钟内最多触发 1 次报警（`SET key value NX EX 300`）
- 滑动窗口：Redis ZSet 按时间戳排序，`ZREMRANGEBYSCORE` 清理过期数据
- 事件驱动：`@EventListener` 异步处理通知和自动创建工单，解耦报警与通知

## 六、服务层（事务与安全要点）

- 所有写操作方法使用 `@Transactional`。
- `AuthServiceImpl.login()` 流程：
  1. 通过 `UserRepository` 查找用户
  2. 调用 `user.login(password)` 执行领域逻辑
  3. `userRepository.save(user)` 保存失败次数/锁定状态
  4. 若登录成功，生成 JWT token 返回
- **事件发布**：MVP 中使用同步日志或简单工具类，暂不启用 `EventBus`。若启用，必须使用 `@TransactionalEventListener(phase = AFTER_COMMIT)` 确保事务提交后发布。

在防刷逻辑部分，加入 Redis 操作说明：

- `MessageServiceImpl.submitMessage()`：
  1. 先执行 Redis 手机号是否存在判断（`StringRedisTemplate.opsForValue().setIfAbsent(phoneKey, "1", 60, TimeUnit.SECONDS)`）。
  2. 再执行 IP 计数限制（`redisTemplate.opsForValue().increment(ipKey)` 并在首次时设置过期时间）。
  3. 通过校验后才执行保存。

### 7.1 RESTful API 设计原则

所有接口严格遵循 RESTful 规范：

- **资源命名**：使用名词复数形式，如 `/products`、`/messages`，表示资源集合。
- **HTTP 方法语义**：
  - `GET`：查询资源（列表或详情）
  - `POST`：创建资源
  - `PUT`：完整更新资源
  - `DELETE`：删除资源（逻辑删除）
- **状态码约定**：与 3.2 节映射规则一致，统一通过 `Result<T>` 返回业务码。
- **版本控制**：通过 URL 前缀 `/api/v1` 管理版本，后续可平滑升级至 v2。
- **过滤、分页**：查询参数如 `?status=PUBLISHED&page=1&size=20` 统一规范。

## 八、安全设计细化

- 密码加密：BCrypt，存储 `passwordHash`。通过 `PasswordHasher` 接口抽象加密逻辑，`BCryptPasswordHasher` 为默认实现。
- **图形验证码**：登录前需调用 `GET /admin/captcha` 获取 4 位数字验证码（Redis 存储，5 分钟有效），登录时需同时提交 `captcha` + `captchaToken`。
- 登录锁定：连续 5 次失败锁定 30 分钟，领域模型内处理，Service 层保存状态。
- JWT 中携带 `userUuid` 和 `role`，用于后续权限判断。
- CORS 仅允许官网域名；`@Valid` 校验输入；XSS 防护由前端转义 + 后端响应头控制。
- **放行路径**：`/api/v1/admin/login`、`/api/v1/admin/captcha`、`/api/v1/public/**` 在安全过滤器链中 `permitAll()`，后台其余接口全部需要认证。
- 权限控制基于 `role` 字段，通过 `@PreAuthorize("hasRole('ADMIN')")` 或配置中的 `hasRole` 表达式实现，未来扩展角色只需要调整表达式或增加枚举值。
- **JWT 黑名单**：管理员主动登出（`POST /admin/logout`）时，将旧 token 存入 Redis，`key = "blacklist:" + tokenId`，过期时间与 token 剩余有效期一致。`JwtAuthFilter` 每次请求检查黑名单，命中则返回 401。
- **前台公开路径**：`/api/v1/public/**` 全部 `permitAll()`。AI 对话接口通过 IP 级别 Redis 限流（10 次/分钟）做防护。
